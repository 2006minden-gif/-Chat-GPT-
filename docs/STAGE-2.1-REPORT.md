## 1. Резервные файлы — исправлено в репозитории, не на SpaceWeb

Подтверждённая причина: прежний public/.htaccess запрещал только имена, начинающиеся с точки, и index.html/crm.html. Имена ~.htaccess и index~.html не соответствовали этим правилам. Повторные production HEAD в этом этапе: оба HTTP 200. Содержимое не скачивалось; наличие секретов в этих файлах не утверждается.

Исправление: FilesMatch с Require all denied блокирует тильду в имени, редакторские #name#, компоненты расширений bak/bkp/backup/old/orig/save/swp/swo/tmp/temp, включая регистр, нумерованные и составные копии. Существующие запреты, DirectoryIndex и Options сохранены. Рабочие файлы приложения и cgi-bin не удаляются.

Файлы: `public/.htaccess`, `tests/test_apache_security.py`. Коммит `d688bca`.

Проверка: настоящий Apache 2.4.69, изолированный document root, синтетическое содержимое. GET/HEAD резервных имён, вложенного пути, URL-encoded ~/#, index.html/crm.html → 403, контрольный маркер отсутствует в ответах. CSS/JS и допустимое имя с текстом backup → 200. Тест со старым .htaccess ожидаемо провалился (41 проверка, включая HTTP 200 вместо 403); с исправлением оба тестовых метода PASS. PHP в статическом Apache-fixture не включён; PHP исполнялся в отдельной интеграционной проверке.

Остаток: production пока отдаёт эти URL; там могут быть другие копии, не покрытые именными шаблонами. После одобрения публикации проверить AllowOverride/применение правил на реальном сервере, затем GET/HEAD обоих URL → 403/404 без содержимого. Содержимое реальных копий нужно проверить приватно на сервере и сохранить нужное вне public_html с ограниченными правами. Без доступа это не сделано; файлы не перемещались и не удалялись. Удаление неизвестных копий требует согласования после проверки.

## 2. Общие 503 — production-причина НЕ установлена

Повторные безопасные GET с проверкой TLS:

| /privacy.php | 503 JSON | 0ccb140f3880e715 |
| /api.php?r=privacy | 503 JSON | 0428e20831ff9f93 |

Это прикладные безопасные ошибки, не доказательство конкретной SQL-проблемы. Общий путь setup и privacy — загрузка private/config.php. GET privacy не использует PDO; изолированный тест подтвердил, что даже при несуществующей БД privacy продолжает работать с корректным config. Повторный импорт схемы не является обоснованным исправлением.

Доступ к журналам отсутствует: TCP к 77.222.40.35:22 из среды возвращает Connection refused; штатный ssh также прекращает работу с Bad owner or permissions on /etc/ssh/ssh_config.d/20-systemd-ssh-proxy.conf. Конфигурация сетевого прокси не обходилась, неизвестный host key не принимался. Нельзя заключить, что SSH выключен именно на стороне SpaceWeb. GitHub REST API из среды отвечает Forbidden; доступ к секретам Actions/серверным журналам через него не получен.

**Отдельный подтверждённый дефект исходников:** при утверждённой политике и существующем, но нечитаемом privacy-policy.txt file_get_contents возвращал false, который попадал в trim под strict_types → TypeError на PHP 8.4. Воспроизведено на исходном коде. Это не доказанная причина наблюдаемых production 503.

Исправление: явная проверка результата чтения, фиксированное событие privacy_policy_unreadable в серверном журнале без путей/текста/секретов; API возвращает enabled=false, страница — понятное уведомление с 503. При неутверждённой политике файл не читается. Страница использует уже проверенный снимок текста, без второго чтения между проверкой и выводом. Формат публичного privacy API сохранён, внутренний текст/хеш не раскрываются им.

Файлы: `private/app.php`, `public/privacy.php`, `tests/test_prelaunch.py`. Коммит `6d8c146`.

Добавлен `scripts/diagnose.php`: только CLI, read-only PDO, никакого создания администратора/лидов/схем. Проверяет PHP/расширения, читаемость и структуру конфига, HTTPS в app_url, отсутствие setup_key, конфигурацию политики, подключение PDO, наличие требуемых столбцов четырёх таблиц, наличие администратора id=1. Проверка столбцов не доказывает правильность всех индексов/ограничений. Выводит статусы и безопасные метаданные исключений, без сообщений исключений, значений конфигурации, SQL, паролей и абсолютных путей. Отсутствующий администратор/активный setup_key дают неуспешную проверку; это не команда что-либо исправлять автоматически.

После получения доверенного SSH-доступа инженер может разместить скрипт **вне public_html**, в `/home/n/neurodepro/scripts/diagnose.php`, и запустить выбранным PHP 8.4 CLI. Его относительный путь обращается к соседнему `/home/n/neurodepro/private/config.php`. Скрипт не является публичным диагностическим URL и сейчас на сервер не загружен. Сначала сопоставить приведённые request ID с приватным error_log, проверить конфиг, права/open_basedir и точку ошибки; затем исправлять только подтверждённую серверную причину.

Тесты: нечитаемый/пустой/отсутствующий документ; экранирование текста; безопасный ответ и корреляция ID при синтаксически повреждённом тестовом config; диагностический отчёт при ParseError и ошибке PDO без утечки секретов/пути/имени БД.
