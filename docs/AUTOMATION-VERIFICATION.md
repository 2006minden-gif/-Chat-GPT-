## Подготовленная система

- Ветка `ci/automatic-spaceweb`: проверки каждого push/PR, публикация актуального main после Validate, последовательные релизы, строго проверенный SSH host key, immutable artifact и контроль hashes, сохранение config/политики/uploads, backup/retention, безопасное файловое восстановление, отрицательный результат при неудачном health.
- Контроллер использует GitHub App при настройке, иначе штатный GITHUB_TOKEN. Во втором случае после native merge он автоматически dispatch-ит CI для актуального main: подавление push-workflows у GITHUB_TOKEN учтено. GitHub App больше не обязателен. Действующие rules/reviews/checks обязательны в обоих вариантах.
- `evidence.yml`, `scripts/github/evidence.py`, `bridge.py`: постоянное чтение результатов без доступа локального окружения к API. Доверяются только main-артефакты; секреты и production-логи не публикуются.
- SQL и CLI runner входят в приватную версионную поставку вне public_html. Автоматический DDL требует проверенный предыдущий healthy release, целый recovery snapshot, успешную baseline-проверку и контракт CI backup/restore. На первой непроверенной поставке 004 заблокирована.
- `verify/stage3-integration` проверяет объединение Stage 3 и доставки. Эта ветка не заменяет PR #4 и не означает разрешённого production DDL.
- `automation/github-control` содержит изолированные read-only проверки GitHub/SSH; не является веткой публикации приложения.

## Что необходимо для завершения

Однократное решение владельца: сохранить приватность и подключить тариф, поддерживающий rulesets, либо отдельно явно разрешить публичность. Публичность автоматически не включать.

Затем необходимы административные права GitHub для первоначальной настройки rules, auto-merge, Actions PR permission и main-only production environment с действующими SSH secrets. Секреты не передавать в чат или Git. Штатный GITHUB_TOKEN не может повысить себе права. Существующие более строгие правила не ослаблять.

SpaceWeb должен восстановить shell для пользователя neurodepro: SSH с текущей автоматизацией отвергается сообщением account unavailable ещё до запуска команды. Требуется проверка состояния аккаунта/SSH на стороне провайдера; изменение приложения это не исправит.

После устранения этих блокировок Codex сможет создать PR, дождаться настоящего review, проверить первое автоматическое файловое обновление и recovery, затем отдельно допустить 004. Сейчас нет оснований утверждать, что production обновлена или CRM проверена end-to-end. Рутинные ZIP, SQL-команды и ручные кнопки deployment в новой схеме не предусмотрены.
