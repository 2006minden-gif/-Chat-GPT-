Это цепочка разработки, а не подтверждение её интеграции в main или публикации. Stage 3 PR #4, Stage 4 PR #7, Stage 5/6 draft PR #21/#22 требуют отдельной проверки интеграции. Stage 9 в доступных исходниках и именованных remote-ветках не найден.

Нет нового провайдера, очереди, механизма релиза или автоматического развертывания. Используются Stage 8 `ai_create`/`ai_run`, бюджеты, идемпотентность, попытки, JSON-контракты и реестр. Добавлено восемь owner-only ролей: coordinator, website, application, agent, design, content, integration, qa с префиксом `production_`. Они генерируют документы и неисполненные артефакты. Наличие роли не означает наличие внешнего инструмента.

## Поток

Подтверждённый заказ + текущая принятая редакция ТЗ Stage 6 + одобренная точная цена Stage 8 + доказательство принятия Stage 9 → неизменяемая редакция плана → проверка → отдельное решение владельца → run → шаги DAG → независимая QA → пакет → отдельное решение владельца → Stage 6 deliverable → принятие клиентом → проверка завершения CRM → отчёт о прибыльности.

Проверка исходников повторяется перед исполнением и передачей. Цена должна совпадать с заказом; применимость каждой версии ставки подтверждается отдельно для вида услуги. Изменение источника останавливает старый план. Изменение принятого плана создаёт новую редакцию, а не меняет одобренную.

`prod_stage9_evidence` сейчас возвращает `STAGE9_ACCEPTANCE_UNAVAILABLE`. Единственное исключение — явно включённый `production_test_mode` с loopback app_url и точным test acceptance fixture в закрытой конфигурации теста. Это не механизм принятия для реального клиента. Без реального адаптера Stage 9 запуск реальных заказов блокируется.

## Данные и миграция 011

`database/migrations/011_ai_production/{up,down}.sql`, runner `scripts/migrate-production.php`.

15 таблиц: `nd_prod_rate_scopes`, `plans`, `runs`, `steps`, `dependencies`, `step_attempts`, `artifacts`, `qa_reports`, `findings`, `revisions`, `packages`, `decisions`, `events`, `expenses`, `profitability` (все с префиксом `nd_prod_`).

Внешние ключи связывают существующие проекты/заказы/администратора, ставки/котировки, AI tasks/artifacts и приватные Stage 6 files/revisions. Составные FK зависимостей удерживают шаги в одном run. Уникальные ключи защищают run на план, попытку на редакцию шага, AI task, решение на точную сущность и файл пакета. Mutable записи имеют версии, артефакты/решения/история сохраняются новыми строками. UTC, InnoDB, utf8mb4, MySQL 5.7; существующие миграции не переписаны.

Runner требует предыдущие миграции, проверяет checksum/journal, удерживает advisory lock и учитывает частичный DDL. Down разрешён только при отсутствии производственных данных; занятые таблицы не удаляет. При частичном применении сначала проверяемый откат пустых новых таблиц, затем повторный up. Не выполнять down для работающего контура: он намеренно откажет. Общая политика удаления и срок хранения истории требует отдельного решения владельца; текущая политика — сохранять доказательства и не удалять их автоматически. Архивный/отменённый проект не допускает продолжение.

## Исполнение и контракты

`private/production/`: contracts/core/plans/engine/artifacts/qa/packages/costs/read/routes/registry/seal.

План ограничен 12 шагами, известными ролями, ациклическими зависимостями, явными файлами и критериями принятого ТЗ. Обязательны `installation.md`, `limitations.md`. Бюджет и валюта явные, максимум доработок 0–3. Конкретная форма примера находится в `tests/test_production.py::plan_body`; это синтетический пример, не коммерческие исходные данные.

Handoff содержит неизменяемые ссылки и SHA256, ID задачи/агента/проекта/заказа/редакции, статус `DRAFT_ONLY`, ограничения и ссылки на входные версии. Тела файлов — данные, не инструкции инструментам. Простые безопасные имена, ограниченные расширения/размеры, запрет traversal. Источник и SHA проверяются сервером. Доступов к SSH/GitHub/SQL или произвольному shell/eval у ролей нет.

CLI `scripts/production-worker.php [run-id]` обрабатывает ограниченный объём, повторное резервирование защищено ключами и DB lock. После неопределённого сбоя новое платное действие не предполагается автоматически успешным. Обычный Stage 8 worker исключает production-задачи; они исполняются только по проверенному отображению одобренного шага. Независимые шаги допустимы в графе, но фактическая конкурентность текущего адаптера 1. Внешнее расписание/постоянный worker не настроены и не подтверждены. Запуск через HTTP не подменяет worker.

Бюджет резервируется консервативно для всех попыток и координатора. Пауза останавливает новые запросы, уже отправленный запрос провайдеру нельзя обещать отменить. Сбой зависимости блокирует потомков. Обновления состояния проверяются сервером; UI не устанавливает произвольный state.

## QA и доставка

QA-роль отделена от производителей. Решение модели не заменяет проверки сервера. Проверяются список файлов, явные `exists/contains` критерии ТЗ, документация, ограниченные признаки опасного кода/секретов и соответствие bundle hash. Это не полноценный анализатор безопасности или смысловой корректности текста.

Любой исполняемый web-артефакт и соответствующий вид услуги требуют runtime/browser/accessibility evidence. Пока sandbox нет, результат `NOT_TESTED`, run `NEEDS_HUMAN`, пакет проверенного приложения недоступен. Нельзя снять это ограничение мнением QA или кнопкой владельца. Документальный результат может пройти конкретные статические критерии; это не обещание работоспособности приложения.

При FAIL допускаются ограниченные редакции; автоматическая доработка отдельно отключена по умолчанию. Результаты прошлых редакций сохраняются, зависимые шаги перепроверяются. Исчерпание лимита передаёт решение владельцу.

Пакет — детерминированный JSON с файлами и checksum, provenance, критериями/результатами QA, инструкциями и ограничениями. Это не автоматически запущенный сайт и не ZIP с распаковкой недоверенного содержимого. Хранение и выдача Stage 6, квоты/приватные права/атомарная запись повторно используются. Обычная загрузка JSON клиентом не включена. Общий редактор файлов не может менять производственный пакет или открыть его клиенту; seal-проверка действует и при выключенном production flag. Только точное подтверждение checksum владельцем и отдельная передача публикуют файл и создают одну существующую Stage 6 процедуру приёмки. Финансовых действий нет.

## Деньги

Реестр ставок, десятичная арифметика, налоги/накладные/маржа и одобрение цены — существующий Stage 8 pricing (`docs/PRICING-STAGES-8-10.md`). Stage 10 не дублирует финансовую модель. Неизвестная/неподтверждённая стоимость требует review, не считается нулём.

Usage собирается со всех попыток и координатора; оценка провайдера и фактическая сумма различаются, NULL остаётся неизвестным, валюты не складываются. Владелец может записать итог категории, источник, время и подтверждение. Новая запись категории — новая версия итога, не повторное суммирование. Только полный подтверждённый RUB-набор позволяет фактический contribution profit; иначе показывается известная часть. Это вклад после учтённых затрат, не бухгалтерская прибыль или расчёт налогового обязательства. Завершение требует действительного customer approval Stage 6, завершённых CRM задач/этапов и сохраняет снимок. Исторические результаты не меняют пороги/опубликованные цены автоматически.

## API и интерфейсы

База: `api.php?r=crm/ai/production/`. Существующие session/origin/CSRF/rate-limit/owner проверки и request_key-idempotency. Клиенту разрешён только scoped GET `projects/{id}` с кратким русским статусом и ссылкой Stage 6; внутренние затраты/промпты/логи недоступны.

Owner GET: settings, overview, plans, plans/{id}, runs, runs/{id}, qa, packages, costs, events, rates.
POST: plans; plans/{id}/{validate,approve,reject,start,revise}; runs/{id}/{pause,resume,revision,package,expense,finish}; packages/{id}/{approve,deliver}; rates/scope. Для решений требуются точная версия/checksum/confirm согласно контракту; версия конфликта возвращает 409, недоступная зависимость также блокирует действие. Общие операции не возвращают приватные исключения.

`public/production.php/js/css` — обзор/заказы/планы/роли/QA/согласование/результаты/стоимость/журнал/ставки, мобильный вид, реальные статусы. `operations.js` связывает CRM и производство; `ai.js` — артефакт координатора и план; portal показывает только безопасный реальный статус. Флаги `production_enabled`, `production_execution_enabled`, `production_auto_revisions_enabled` false по умолчанию; privacy flags не меняются.
