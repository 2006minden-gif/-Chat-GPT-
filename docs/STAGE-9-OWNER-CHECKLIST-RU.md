# Stage 9 — проверка владельцем

Это инструкции к тестовой версии, а не подтверждение публикации neurodelo.pro. На production флаги/миграции/автоматизация не менялись. Не нужны новые аккаунты сотрудников, Codex API или платёжные ключи.

1. В `/catalog-owner.php#templates` создайте анкету. Можно добавить шаги/вопросы конструктором и отредактировать JSON: название, назначение ответа, required, bounds, варианты, условия. Пример ниже — только структура, не утверждённая услуга. Сохраните и отдельно опубликуйте точную редакцию. Запомните показанный ID редакции, не ID родительской анкеты.
2. В `#services` создайте услугу: название/описание, категория, состав работ, результаты, estimate/fixed, пакеты, Telegram и ID опубликованной редакции анкеты. Оценочные пакеты и количества внутренние; клиент их не получает. Время вашей проверки/исправлений заполните явно; null не заменяется нулём. Эти часы добавляются сервером отдельно, не дублируйте их в обычных пакетах работ. Даже AI-ответ не убирает неизвестное время из модели.
3. Сохраните услугу: прежняя публикация остаётся прежней. Проверьте и отдельно нажмите «Опубликовать точную редакцию». Изменённый несохранённый JSON публиковаться не должен. Проверяйте «Показанная редакция» и активную публикацию. Снять с публикации/архивировать можно без удаления истории.
4. В `/catalog.php` должны отображаться только ваши опубликованные данные. Если приём брифов не настроен/юридически не одобрен, entry закрыт. Сайт не должен показывать придуманные услуги, цены или готовность оплаты.
5. Под существующим тестовым клиентом откройте «Заполнить бриф». Отдельное согласие изначально снято. Создайте черновик, заполните шаги и условные вопросы, сохраните. Перезагрузите: ответы восстановлены, согласие заново не проставлено автоматически.
6. Вложения загружаются в защищённый проект. Не указывайте пароли/API-ключи/платёжные реквизиты. Неисполняемые допустимые файлы работают, PHP/чужие project IDs отклоняются.
7. Проверьте ответы на review шаге и отправьте бриф. В `/workspace.php#leads` и `#deals` должны появиться ровно одна заявка/сделка, привязанные к существующему клиенту. Заказ ещё не создаётся. `/catalog-owner.php#requests` показывает буквальные ответы и версии.
8. Владелец открывает «Расчёт и одобрение цены» (существующий pricing компонент). Реестр `#rates` содержит ставки с источником/датой/валютой/периодом, явную трактовку налогов и минимум доходности. Эти бизнес-данные утверждаете вы, приложение их не выдумывает.
9. Автоматическая оценка использует модель услуги/typed quantities, включая вашу проверку/исправления. Если неизвестны часы/ставки/правила, ожидается NEEDS_COST_REVIEW. При уже разрешённом AI может быть создано отдельное cost_estimator задание; без live provider нельзя обещать настоящий AI-анализ. Детальная арифметика работает без AI-ключей.
10. Одобрите точную цену либо создайте новую редакцию/пересчёт/отклонение. Низкая доходность и неизвестные расходы не должны одобряться. Материальное изменение brief/project/rates требует новой проверки; старые снимки не переписываются.
11. В карточке заявки заполните свои проверенные условия, срок действия предложения (UTC), при необходимости одобренный срок работ. Можно указать готовый артефакт существующего proposal agent только для того же проекта/цены. «Подготовить черновик предложения» ещё не отправляет его клиенту.
12. Прочитайте текст, ТЗ, состав, цену и условия. «Одобрить и отправить точное предложение» — отдельное решение владельца. Только после этого клиент видит предложение.
13. Клиент читает brief и «Точная редакция ТЗ», принимает предложение и отдельно подтверждает заказ. Новый confirmed order должен появиться в существующей CRM и кабинете. Повторные/одновременные confirm не создают второй order.
14. Новая редакция до подтверждения делает прежнее предложение неактуальным. Cancel сохраняет историю и закрывает связанную сделку/проект. Уже созданный заказ отменяется через owner CRM, не удалением финансовой истории.
15. После подтверждения доступны существующие проект/документы/счета при включённом модуле. Проверяйте только test invoice, без реального платежа. Stage10 может проверить настоящее принятие оферты; отсутствие sandbox/provider по-прежнему блокирует технически непроверенное исполнение.
16. Второй тестовый клиент не видит чужие drafts/briefs/offers/invoices/files. В браузере ошибки не очищают ответы и неожиданный HTML не превращается в сообщение об успехе.

Примеры схем — `docs/stage-9-examples/`. Это учебные заготовки с неизвестными затратами; они не загружаются в production и не являются утверждёнными ценами/услугами.

До выпуска остаются отдельные technical gates Stage12: полный deploy package, поддержанный safe migration operator, actual hosting/backup/recovery/protection evidence и согласованные правовые/бизнес-данные. Повторного per-release разрешения на публикацию владелец не должен давать, но проваленный gate не обходится.
